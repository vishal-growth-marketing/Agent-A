# EXECUTION PLAYBOOK

### Version: 1.0
### Owner: Team Leader
### Status: LIVE — Every Skill and Orchestrator reads this before execution.

---

# WHAT THIS FILE IS

Execution defines how work happens inside this operating system.

If Constitution answers:

> **"What must never change?"**

Execution answers:

> **"How do we work today?"**

Execution is the shared operational context for the entire system.

Every skill and orchestrator must read this file before reading its own role file.

Voice, terminology, current positioning, approved claims, pricing, content priorities, active campaigns, operating preferences, known constraints, verified facts, and open decisions all belong here.

Execution is expected to evolve constantly.

Constitution should rarely change.

---

# READ ORDER

Every task follows the same order.

```
Constitution
        ↓
Execution
        ↓
Role
```

No skill or orchestrator should execute using only its own role definition.

Execution ensures every specialist starts from the same business reality.

---

# OPERATING PRINCIPLES

## Rule 1 — Solve Today's Problem

Every task executes against today's business reality.

Never reuse old assumptions simply because they existed in a previous session.

If pricing changes,
Execution changes.

If positioning changes,
Execution changes.

If ICP changes,
Execution changes.

Execution is the living operational state of the company.

---

## Rule 2 — One Source of Operational Truth

If Execution defines:

- terminology
- pricing
- buyer segments
- messaging
- campaign priorities
- content priorities
- SEO priorities
- GEO priorities

every skill uses exactly that version.

Skills adapt to Execution.

Execution never adapts to individual skills.

---

## Rule 3 — Unknown Stays Unknown

Execution documents decisions.

It does not invent them.

Missing information remains listed as **Pending** until confirmed.

Never convert uncertainty into policy.

---

## Rule 4 — Every Rule Must Help Someone Execute

Execution exists to help specialists make better decisions.

If a rule cannot change how a skill executes,

it probably belongs somewhere else.

Avoid documentation for documentation's sake.

---

## Rule 5 — Change Deliberately

Operational changes happen frequently.

Execution records:

- what changed
- why it changed
- when it changed
- who approved it

Nobody should wonder why the system behaves differently than yesterday.

---

# OPERATING STATE

Execution should always contain the current business state, including:

- Current positioning
- Current ICP
- Current category
- Current pricing
- Approved terminology
- Brand voice & writing preferences
- Active campaigns
- Current quarter priorities
- Current content priorities
- Current SEO priorities
- Current GEO priorities
- Verified statistics and approved sources
- Active experiments
- Known constraints
- Pending decisions
- Operational changelog

Delete sections that don't apply.

Execution should remain focused and practical.

---

# WHAT NEVER BELONGS HERE

Execution never defines:

- Company identity
- Legal claims or policies
- Constitutional rules
- Governance hierarchy
- Permanent brand principles
- Specialist responsibilities
- Skill-specific reasoning
- Prompt instructions

Those belong in Constitution or the relevant role file.

---

# CONFLICT RULE

If anything in Execution conflicts with Constitution,

**Constitution always wins.**

The role stops, reports the conflict to Team Leader, and waits for human direction.

Execution never overrides governance.

---

# SELF-CHECK

Before updating Execution, ask:

> Did I document reality,
> or did I accidentally create new reality?

Execution reflects business decisions.

It never makes them.

If the answer is unclear,

stop and ask before updating.
